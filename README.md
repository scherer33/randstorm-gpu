# RandStorm — CUDA GPU Implementation

A GPU-accelerated implementation of the RandStorm weak-PRNG vulnerability, built on the original research by [RandstormBTC](https://github.com/RandstormBTC/randstorm).

## The vulnerability

Between 2011 and 2015, wallets generated by BitcoinJS-lib v0.1.3 seeded their RNG from `Math.random()` in environments where `window.crypto.getRandomValues` was unavailable. The seed is the wallet creation timestamp in Unix milliseconds, so for a known address there are only ~10⁹ candidates to search instead of 2²⁵⁶.

## What this implementation adds

The original is a Python reference implementation. Recovering a seed space of 1.4 billion candidates is CPU-bound on scalar modular arithmetic: each candidate needs a secp256k1 scalar multiplication and a modular inversion.

The core optimisation here is **batch inversion** using Montgomery's trick. Given N field elements, compute one modular inverse and N-1 multiplications, instead of N inversions. Since a seed range search produces keys in bulk, the inversion cost is amortised across the whole batch.

Supporting work:

- **EC precomputation table** (`src/ec_table.rs`) — a windowed table of small multiples of the generator, uploaded to the GPU once and reused for every scalar multiplication.
- **32-bit limb field arithmetic** (`kernel/secp256k1_32.cuh`) — limb layout matches the host-side table so precomputed points upload without repacking.
- **Split pipeline** — `randstorm_pk_to_jacobian` and `randstorm_jacobian_to_hash160` are separate kernels, so the inversion happens once per batch between them rather than per key.
- **Verification harnesses** (`examples/`) — scalar multiplication, point doubling, inversion and reference cross-checks.

## Repository layout

Two crates are present. **`rust/` is the current implementation.**

| | `rust/` (current) | `randstorm-cuda/` (legacy) |
|---|---|---|
| Package | `randstorm` | `randstorm-cuda` |
| CUDA kernel | batch inversion pipeline | single fused kernel |
| PRNG | `src/prng.rs` module | inline in `main.rs` |
| Library target | yes, unit-testable | minimal |
| Exported symbols | 6 | 6 |

The legacy crate is kept because it shows the simpler single-kernel formulation the batch inversion pipeline replaced. Build and run `rust/`.

## Building

Requires the CUDA toolkit (`nvcc`) for GPU mode. Without it the build falls back to CPU-only automatically and `cargo run -- --no-cuda` is implied.

```bash
cd rust
cargo build --release
```

The kernel compiles for `sm_75` (Turing) by default. Change `-arch=sm_75` in `build.rs` for other architectures.

Set `CUDA_HOME` if your toolkit is not at `/opt/cuda`:

```bash
CUDA_HOME=/usr/local/cuda cargo build --release
```

## Usage

```bash
./target/release/randstorm \
  --target <address> \
  --start <unix-ms> \
  --end <unix-ms> \
  --batch-size 16384
```

| Flag | Default | Description |
|---|---|---|
| `--target` | `1LdRcdxfbSnmCYYNdeYpUnztiYzVfBEQeC` | Address to search for |
| `--start` | `1388534400000` | Seed range start, Unix milliseconds |
| `--end` | `1401234582000` | Seed range end, Unix milliseconds |
| `--batch-size` | `16384` | Keys per inversion batch. Larger amortises inversion better, at the cost of GPU memory |
| `-v`, `--v8seed` | `0xDEADBEEF` | Seed for the xorshift128+ state |
| `-o`, `--output` | `randstorm_results.txt` | Results path |
| `--no-cuda` | `false` | Force CPU-only |
| `-t`, `--threads` | `0` | CPU threads, `0` = all cores |

Converting a first-transaction date to a seed bound:

```bash
date -d "2014-03-16 23:48:51 GMT -7" +"%s" | awk '{print $1 * 1000}'
```

## Verification

```bash
cd rust
cargo run --release --example test_reference
cargo run --release --example test_scalars
cargo run --release --example test_inv
```

`test_reference` cross-checks GPU output against the `bitcoin` crate's own secp256k1 implementation. If these disagree, the pipeline is wrong regardless of throughput.

## Responsible use

This is for wallet recovery research and forensic analysis of your own keys.

Affected wallets are already publicly catalogued. If you find a funded address generated with BitcoinJS-lib v0.1.3, **report it to the exchange or service that holds it** rather than sweeping it. Wallets that received funds in good faith are not attackers, and the recovery belongs to whoever legitimately owns the key.
